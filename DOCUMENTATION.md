# Документация проекта PromptLearn / Prompt Academy

---

## 1. Общее описание

**Название:** Prompt Academy (фронтенд, бренд).

**Назначение:** Платформа для обучения промпт-инжинирингу: курсы, практические задания, анализ промптов (в т.ч. через внешний ИИ или эвристики), рейтинг, профиль пользователя, админ-панель.

**Стек:**
- **Backend:** Node.js, Express, SQLite3, JWT, bcrypt, uuid, nodemailer (SMTP-письма).
- **PDF сертификатов:** Playwright (Chromium) — серверная генерация PDF 1:1 по HTML.
- **Frontend:** статический HTML + CSS + vanilla JavaScript (ES modules), без фреймворков.
- **База данных:** один файл SQLite (`database.db` по умолчанию).

## 2. Структура проекта

### 2.0. Что означают каталоги (словарик)

Ниже — краткое объяснение, **зачем нужны папки** и как между собой связаны части бекенда/фронтенда.

#### Backend

- **`backend/routes/`**: “карта API”.
  - Здесь объявляются HTTP-маршруты (`GET/POST/PUT/...`) и привязываются к обработчикам из `controllers`.
  - Также здесь подключаются промежуточные проверки (`middleware`), например авторизация.

- **`backend/controllers/`**: бизнес-логика endpoint’ов.
  - Каждый контроллер — набор функций-обработчиков для конкретной области: `auth`, `tasks`, `profile`, `courses`, `admin` и т.д.
  - Контроллеры валидируют входные данные, вызывают `models` (работа с БД), `utils` (вспомогательные функции) и формируют JSON-ответ.

- **`backend/models/`**: слой работы с БД (SQLite).
  - Здесь лежат функции, которые выполняют SQL-запросы (`SELECT/INSERT/UPDATE/DELETE`) и возвращают данные контроллерам.
  - Важно: модели не должны “знать” про HTTP — только про данные и SQL.

- **`backend/middleware/`**: промежуточные обработчики Express.
  - Это функции вида `(req, res, next)`, которые выполняются **до** контроллера.
  - Примеры: проверка JWT (`authMiddleware`), проверка роли админа (`adminMiddleware`), запрет действий до подтверждения email (`requireVerifiedEmail`).

- **`backend/utils/`**: утилиты и интеграции.
  - Вспомогательные модули, которые не относятся напрямую к роутингу/БД: отправка писем (`mailer.js`), работа с AI (`aiAnalyzer.js`) и т.п.

- **`backend/db/`**: инфраструктура SQLite.
  - `db.js` — подключение к файлу базы.
  - `initDB.js` — создание схемы таблиц и “мягкие миграции”.
  - вспомогательные скрипты для разработки (например очистка/сиды).

- **`backend/scripts/`**: одноразовые/админские скрипты, которые запускаются вручную (CLI).
  - Например создание администратора.

#### Frontend

- **`frontend/*.html`**: страницы приложения (статический фронт без сборщика).
  - Переходы между страницами — обычные переходы по URL.

- **`frontend/js/`**: JS-логика страниц (ES modules).
  - `api.js` — единый клиент для вызова бекенда (`/api/...`).
  - Остальные файлы обычно соответствуют страницам (`profile.js` → `profile.html`).

- **`frontend/js/admin/`** и **`frontend/admin/`**: админка.
  - `frontend/admin/*.html` — страницы админки.
  - `frontend/js/admin/*.js` — логика этих страниц (CRUD, конструктор курсов и т.п.).

- **`frontend/styles.css`**: глобальные стили и компоненты UI (кнопки, модалки, навбар, карточки).

### 2.1. Backend: назначение ключевых файлов

- **`backend/server.js`**: единая точка входа.
  - включает CORS, JSON-parsing;
  - раздаёт статику фронта (`frontend/`) и `backend/uploads/` по `/uploads`;
  - подключает API-роуты `/api/*`;
  - запускает `initDB()`;
  - содержит редирект совместимости для старых ссылок подтверждения: `/verify-email?token=...` → `/profile?verifyToken=...`.

- **`backend/config.js`**: читает переменные окружения из `backend/.env` и экспортирует конфиг.

- **`backend/db/initDB.js`**: создаёт все таблицы (и добавляет новые колонки через `ALTER TABLE ... ADD COLUMN`, чтобы поддерживать уже существующую базу).

- **`backend/utils/mailer.js`**: SMTP-отправка писем через `nodemailer`. Проверяет, что SMTP настроен, иначе кидает ошибку `MAIL_NOT_CONFIGURED`.

- **`backend/controllers/authController.js`**: вся логика авторизации и “почтовых” сценариев:
  - `register`, `login`;
  - `verifyEmail`, `resendVerification`;
  - `forgotPassword`, `resetPassword`;
  - формирует ссылки из `APP_BASE_URL` и отправляет письма через `mailer`.

- **`backend/middleware/requireVerifiedEmail.js`**: блокирует действия до подтверждения email. Используется на маршрутах:
  - `/api/prompts/analyze`
  - `/api/tasks/submit`
  - защищённые действия курсов (`enroll`, `complete`, `quiz`, `steps`).

### 2.2. Frontend: назначение ключевых файлов

- **`frontend/login.html`**: форма входа + модалки:
  - “Забыли пароль?” (ввод email → письмо);
  - “Новый пароль” (открывается автоматически при `?resetToken=...`).

- **`frontend/profile.html` + `frontend/js/profile.js`**:
  - личный кабинет;
  - UI статуса email (подтверждён/нет) + кнопка resend;
  - модалка подтверждения email:
    - открывается после регистрации (`/profile?needsEmailVerify=1`);
    - подтверждает по ссылке из письма (`/profile?verifyToken=...`).

- **`frontend/js/api.js`**:
  - единый `request()` для API;
  - выбрасывает `ApiError` с `status` и `retryAfterSeconds` (для лимитов отправки писем);
  - содержит методы `apiResendVerification`, `apiVerifyEmail`, `apiForgotPassword`, `apiResetPassword`.

| SMTP_PASS   | Пароль SMTP (лучше “пароль приложения”) | '' |

**Запуск:**
- Из корня проекта: в папке `backend` выполнить `npm install`, затем `npm start` (или `npm run dev` с nodemon).
- Фронтенд раздаётся самим Express из `frontend/` (`express.static`), т.е. приложение доступно по `http://localhost:PORT` (например 5000).

**Инициализация БД:**  
`node backend/db/initDB.js` или скрипт `npm run initdb` из папки backend. Таблицы создаются при первом запуске `server.js` (вызов `initDB()`).

**Создание админа:**  
`node backend/scripts/createAdminUser.js [email] [password] [name]`  
По умолчанию: email `admin@promptlearn.local`, password `admin123`, name `Admin`. Если пользователь есть — ему выставляется роль `admin`.

## 4. База данных (SQLite)

База — один файл SQLite (`backend/database.db` или путь из `DB_PATH`). Схема создаётся/обновляется в `backend/db/initDB.js`.

### 4.1. Таблица `users`

Хранит аккаунты пользователей платформы.

| № | Поле | Тип | Размер/Ограничения | Описание |
|---|------|-----|-------------------|----------|
| 1 | `id` | TEXT | PRIMARY KEY | Уникальный идентификатор пользователя (UUID v4). Генерируется автоматически при регистрации. |
| 2 | `email` | TEXT | UNIQUE, NOT NULL | Адрес электронной почты пользователя. Используется как логин для входа в систему. |
| 3 | `password_hash` | TEXT | NOT NULL | Хэш пароля пользователя, созданный с помощью bcrypt (10 раундов). Не хранит пароль в открытом виде. |
| 4 | `name` | TEXT | NOT NULL | Отображаемое имя пользователя. Видно в рейтинге, профиле и других разделах платформы. |
| 5 | `role` | TEXT | DEFAULT 'user' | Роль пользователя в системе. Возможные значения: 'user' (обычный пользователь), 'admin' (администратор). |
| 6 | `points` | INTEGER | DEFAULT 0 | Суммарное количество очков активности. Начисляется за выполнение заданий, прохождение курсов, активность в лаборатории. |
| 7 | `level` | INTEGER | DEFAULT 1 | Уровень пользователя. Вычисляется по формуле: level = 1 + floor(points / 500). |
| 8 | `created_at` | TEXT | DEFAULT datetime('now') | Дата и время регистрации пользователя в системе (в формате SQLite datetime). |
| 9 | `last_seen_at` | TEXT | NULLABLE | Дата и время последней активности пользователя. Обновляется при каждом запросе с валидным JWT токеном. |
| 10 | `email_verified_at` | TEXT | NULLABLE | Дата подтверждения адреса электронной почты. NULL означает, что email не подтверждён. Заполняется после перехода по ссылке из письма. |

**Описание записей таблицы «users»:**

«id» — первичный ключ таблицы, который является уникальным идентификатором пользователя в формате UUID v4. Значение генерируется автоматически при добавлении каждой новой записи с использованием функции uuidv4() из пакета uuid.

«email» — запись строкового типа данных, хранящая адрес электронной почты пользователя. Поле уникально (UNIQUE constraint) и обязательно для заполнения (NOT NULL). Используется как логин при входе в систему.

«password_hash» — запись строкового типа данных, хранящая хэш пароля пользователя. Пароль хэшируется алгоритмом bcrypt с 10 раундами. Исходный пароль не хранится в системе.

«name» — запись строкового типа данных, хранящая отображаемое имя пользователя. Видно в рейтинге, личном кабинете и других разделах. Обязательно для заполнения при регистрации.

«role» — запись строкового типа данных, определяющая роль пользователя в системе. По умолчанию 'user'. Возможные значения: 'user' (обычный пользователь) или 'admin' (администратор платформы).

«points» — запись целочисленного типа данных, хранящая суммарное количество очков активности пользователя. Начисляется за выполнение практических заданий, прохождение курсов, анализ промптов в лаборатории. Используется для определения места в рейтинге и лиги.

«level» — запись целочисленного типа данных, представляющая уровень пользователя. Вычисляется автоматически на основе очков: level = 1 + floor(points / 500). При 0 очках уровень 1, при 500 очках — уровень 2, и т.д.

«created_at» — запись текстового типа данных, содержащая дату и время регистрации пользователя. Заполняется автоматически функцией datetime('now') при создании записи.

«last_seen_at» — запись текстового типа данных, хранящая дату и время последней активности пользователя. Обновляется middleware authMiddleware при каждом запросе с валидным JWT токеном. NULL при регистрации.

«email_verified_at» — запись текстового типа данных, содержащая дату подтверждения электронной почты. Заполняется после перехода пользователя по ссылке из письма с подтверждением. NULL означает, что email не подтверждён, что ограничивает некоторые действия (анализ промптов, отправка решений).

### 4.2. Таблица `email_verification_tokens`

Хранит одноразовые токены для подтверждения адреса электронной почты. В таблице хранится только хэш токена, сам токен передаётся пользователю в ссылке письма.

| № | Поле | Тип | Размер/Ограничения | Описание |
|---|------|-----|-------------------|----------|
| 1 | `id` | TEXT | PRIMARY KEY | Уникальный идентификатор токена (UUID v4). Генерируется автоматически при создании токена. |
| 2 | `user_id` | TEXT | NOT NULL, FOREIGN KEY | Ссылка на таблицу users.id. Определяет, какому пользователю принадлежит токен. |
| 3 | `token_hash` | TEXT | NOT NULL | Хэш токена подтверждения, созданный алгоритмом SHA-256. Сам токен не хранится, только его хэш. |
| 4 | `expires_at` | TEXT | NOT NULL | Дата и время истечения срока действия токена. После этого времени токен не может быть использован. |
| 5 | `used_at` | TEXT | NULLABLE | Дата и время использования токена. Заполняется при успешном подтверждении email. После использования токен больше недействителен. |
| 6 | `created_at` | TEXT | DEFAULT datetime('now') | Дата и время создания токена. Заполняется автоматически при добавлении записи. |

**Описание записей таблицы «email_verification_tokens»:**

«id» — первичный ключ таблицы, уникальный идентификатор токена в формате UUID v4. Генерируется автоматически при создании новой записи.

«user_id` — запись строкового типа данных, содержащая ссылку на пользователя, для которого создан токен. Является внешним ключом к таблице users. Обязательна для заполнения (NOT NULL).

«token_hash` — запись строкового типа данных, хранящая хэш токена подтверждения email. Токен хэшируется алгоритмом SHA-256 перед сохранением. Сам токен в открытом виде не хранится в системе, только в ссылке, отправляемой пользователю на email.

«used_at` — запись текстового типа данных, содержащая дату и время использования токена. Заполняется NULL при создании и получает значение после успешного подтверждения email пользователем. После использования токен становится недействительным (one-time использование).

«created_at` — запись текстового типа данных, содержащая дату и время создания токена. Заполняется автоматически функцией datetime('now') при добавлении записи в таблицу.

### 4.4. Таблица `auth_rate_limits`

Хранит информацию о лимитах отправки запросов на "почтовые" эндпоинты (запрос сброса пароля, повторная отправка подтверждения email). Предназначена для предотвращения злоупотреблений и защиты SMTP-сервера от перегрузки.

| № | Поле | Тип | Размер/Ограничения | Описание |
|---|------|-----|-------------------|----------|

| 3 | `key` | TEXT | NOT NULL | Ключ лимита — IP-адрес или email пользователя в зависимости от scope. |
| 4 | `window_start_ms` | INTEGER | NOT NULL | Время начала текущего окна лимита в миллисекундах (epoch time). |

**Описание записей таблицы «auth_rate_limits»:**

«key» — запись строкового типа данных, содержащая ключ лимита. В зависимости от scope это может быть IP-адрес пользователя или его email. Например, при scope='forgot_password:ip' key будет содержать IP-адрес.

«window_start_ms» — запись целочисленного типа данных, хранящая время начала текущего окна лимита в миллисекундах (Unix epoch time). Используется для определения, когда началось текущее окно времени для подсчёта запросов.

«count» — запись целочисленного типа данных, содержащая количество запросов, сделанных в текущем окне времени. Увеличивается при каждом запросе соответствующего типа. При превышении лимита возвращается ошибка 429.

«created_at» — запись текстового типа данных, содержащая дату и время создания записи. Заполняется автоматически.

«updated_at» — запись текстового типа данных, содержащая дату и время последнего обновления записи. Обновляется при каждом изменении счётчика или сбросе окна.

| 2 | `lesson_id` | TEXT | NOT NULL, FOREIGN KEY | Ссылка на таблицу course_lessons.id. Урок, к которому принадлежит шаг. |
| 3 | `step_type` | TEXT | NOT NULL, CHECK | Тип шага: 'theory', 'video', 'test', 'practical'. |
| 4 | `order_index` | INTEGER | DEFAULT 0 | Порядковый номер шага в уроке. |
| 5 | `payload` | TEXT | NULLABLE | JSON-данные шага (зависят от типа). |

**Описание записей таблицы «course_lesson_steps»:**

«id» — первичный ключ таблицы, уникальный идентификатор шага в формате UUID v4.

«lesson_id» — запись строкового типа данных, содержащая ссылку на урок, к которому принадлежит шаг. Внешний ключ к таблице course_lessons.

«step_type» — запись строкового типа данных, определяющая тип шага. Возможные значения: 'theory' (теория/текст), 'video' (видео), 'test' (тест), 'practical' (практическое задание).

«order_index» — запись целочисленного типа данных, определяющая порядковый номер шага в уроке. Используется for сортировки шагов.

«payload» — запись текстового типа данных, содержащая JSON-строку с данными шага. Формат зависит от типа:
- theory: `{ "content": "текст теории" }`
- video: `{ "title": "название", "url": "ссылка на видео", "description": "описание" }`
- test: `{ "question": "вопрос", "options": [...], "correctIndex": 0 }`
- practical: `{ "task": "задание", "hints": [...] }`

## 5. API

Базовый URL: `/api`. Все ответы с ошибкой — JSON с полем `message` (строка). Успешные ответы — JSON (кроме 204).

### Авторизация

- В запросах, требующих авторизации, заголовок:  
  `Authorization: Bearer <JWT>`
- Токен на фронтенде хранится в `localStorage` под ключом `promptlearn_auth` в виде объекта `{ token: "..." }` (см. `frontend/js/api.js`: `getStoredToken()`).

### 5.1. Публичные маршруты

| Метод | Путь | Описание |
|-------|------|----------|
| GET | /api/health | Health-check: `{ status, message }` |
| POST | /api/auth/register | Регистрация. Body: `{ email, password, name }`. Ответ: `{ token, user }` |
| POST | /api/auth/login | Вход. Body: `{ email, password }`. Ответ: `{ token, user }` |
| GET | /api/auth/verify-email | Подтверждение email по токену. Query: `token`. Ответ: `{ message }` |
| POST | /api/auth/forgot-password | Запросить письмо сброса пароля. Body: `{ email }`. Ответ всегда "Если email зарегистрирован…" |
| POST | /api/auth/reset-password | Сбросить пароль. Body: `{ token, newPassword }`. Ответ: `{ message }` |
| GET | /api/tasks | Список всех заданий (массив объектов task) |
| GET | /api/tasks/:id | Одно задание по id |
| GET | /api/leaderboard | Топ пользователей по очкам (массив: id, name, email, points, level) |
| GET | /api/leaderboard/enhanced | Расширенный рейтинг с лигами и достижениями. Query: `limit` (по умолчанию 25, макс 100). Ответ: `{ leaderboard: [...], showing: number }` |
| GET | /api/achievements | Каталог всех достижений с прогрессом (если авторизован). Опционально с JWT. Ответ: `{ achievements: [...], totalUsers, rareShowcase: [...] }` |

### 5.2. С авторизацией (JWT)

| Метод | Путь | Описание |
|-------|------|----------|
| POST | /api/prompts/analyze | Анализ промпта. Body: `{ prompt }`. Ответ: `{ aiResponse, analysis }` |

| POST | /api/auth/resend-verification | Повторно отправить письмо подтверждения email (требует JWT) |

#### Требование подтверждения email

Некоторые действия доступны только при `users.email_verified_at IS NOT NULL`:
- `/api/prompts/analyze`
- `/api/tasks/submit`
- защищённые действия курсов (enroll/complete/quiz/steps)

Если email не подтверждён — ответ `403`:
```json
{ "message": "Подтвердите email, чтобы продолжить.", "code": "EMAIL_NOT_VERIFIED" }
```

#### Лимиты отправки писем (rate-limit)

Для `forgot-password` и `resend-verification` включён персистентный rate-limit (SQLite). При превышении возвращается `429`:
- JSON содержит `retryAfterSeconds`
- также устанавливается HTTP заголовок `Retry-After`

#### Видео в курсах (шаг `video`)

Шаги уроков хранятся в таблице `course_lesson_steps`. Для `step_type = "video"` используется `payload`:
- `payload.title` — заголовок
- `payload.url` — ссылка на видео
- `payload.description` — описание (опционально)

Поддерживаются два сценария:
- **Загруженный файл**: через админский endpoint `POST /api/admin/lessons/:lessonId/videos` (multipart `file`).
  - Сервер сохраняет файл в `backend/uploads/...` и возвращает `url` вида **`/uploads/...`**
  - Этот URL сохраняется в `payload.url`
  - На странице урока (`frontend/js/course.js`) такой URL отображается встроенным плеером: `<video controls>`
- **Внешняя ссылка (например YouTube)**: можно вручную указать в `payload.url`
  - На странице урока такая ссылка отображается через `<iframe>` (embed для YouTube)

Примечания:
- Загрузка видео работает только для уже сохранённого урока (нужен `lessonId`).
- Ограничения загрузки видео задаются в `backend/middleware/uploadMiddleware.js` (`uploadVideoSingle`): размер и список расширений.

Формат полей заданий (tasks): `id`, `title`, `description`, `difficulty`, `points`, `type`. При создании `id` генерируется на бэкенде (uuid).

## 6. Анализ промптов (ИИ и эвристики)

Модуль: `backend/utils/aiAnalyzer.js`.

- **analyzePrompt(prompt)** — основная функция, возвращает объект анализа.
- Если в конфиге заданы `AI_API_URL` и `AI_API_KEY`, вызывается внешний API:
  - Запрос: `POST` на `AI_API_URL`, заголовок `Authorization: Bearer <AI_API_KEY>`, body: `{ prompt }`.
  - Ожидается JSON-ответ, который целиком считается результатом анализа (должен содержать поля вроде `aiResponse`, `clarity`, `structure`, `specificity`, `effectiveness`, `suggestions` при необходимости).
- Если внешний API не настроен или не вернул объект — используется **эвристический анализ** `buildHeuristicAnalysis(prompt)`:
  - Учитывает длину текста, наличие примеров (например|example|e.g.), нумерованных шагов.
  - Возвращает: `clarity`, `structure`, `specificity`, `effectiveness` (числа до 10), `suggestions` (строка), `aiResponse` (строка с рекомендациями).

На фронтенде в `api.js` есть `normalizeAnalysisToFive(analysis)` — переводит числовые оценки (например 1–10) в шкалу 1–5 для отображения.

## 8. Важные соглашения для доработки

- Сообщения пользователю и логи на бэкенде — на **русском** (например: «Требуется авторизация», «Задание не найдено»).
- Идентификаторы сущностей — **UUID** (пакет `uuid`, v4).
- Пароли: хеширование **bcrypt** (в authController — 10 раундов).
- JWT: в payload — `id`, `email`, `role`; срок жизни — 7 дней.
- При отправке решения по заданию пользователю начисляются очки задания (`task.points`), результат сохраняется в `task_results`, анализ вызывается через `analyzePrompt` (внешний ИИ или эвристики).
- Бэкенд не использует TypeScript; фронтенд — без сборщика (чистый JS и HTML/CSS).

### 9.6. Прокси (nginx) и HTTPS

Если перед Node стоит **nginx**: виртуальный хост слушает 443, SSL выдаётся certbot’ом или панелью хостинга; в `location /` задаётся прокси на приложение, например:

```nginx
location / {
    proxy_pass http://127.0.0.1:5000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

Порт `5000` замените на ваш `PORT`. Загрузка файлов в админке (курсы) использует те же лимиты тела запроса — при больших вложениях при необходимости увеличьте `client_max_body_size` в nginx.

## 10. Админ-дашборд с графиками

### 10.1. Обзор

Админ-панель включает современный дашборд с визуализацией данных в реальном времени. Доступен по адресу `/admin/dashboard` для пользователей с ролью `admin`.

### 10.2. Компоненты дашборда

#### Статистические карточки
- **Всего пользователей** — общее количество зарегистрированных пользователей
- **Всего заданий** — количество заданий в системе
- **Промптов в библиотеке** — количество записей в библиотеке промптов
- **Активные пользователи** — пользователи, выполнившие хотя бы одно задание

#### Графики (используется Chart.js)

1. **Регистрация пользователей (7 дней)** — линейный график с площадью
   - Показывает динамику регистрации новых пользователей
   - Источник: `userTrend` из `/api/admin/stats`

2. **Статус заданий** — кольцевая диаграмма (doughnut)
   - Выполнено (зелёный) — результаты с `score > 0`
   - В процессе (синий) — результаты с `score = 0` или `NULL`

3. **Задания по сложности** — столбчатая диаграмма
   - Лёгкие (зелёный), Средние (жёлтый), Сложные (красный)
   - Источник: `difficultyDist` из `/api/admin/stats`

4. **Категории промптов** — круговая диаграмма (pie)
   - Обучение, Код, Тон и стиль, Другое
   - Источник: `categoryDist` из `/api/admin/stats`

5. **Популярность курсов** — горизонтальная столбчатая диаграмма
   - Топ-5 курсов по количеству записей
   - Источник: `courseStats` из `/api/admin/stats`

### 10.3. Файлы реализации

- **Backend:** `backend/controllers/adminController.js` — функция `getStats()`
- **Frontend HTML:** `frontend/admin/dashboard.html`
- **Frontend JS:** `frontend/js/admin/dashboard.js`
- **Стили:** встроены в `dashboard.html` + общие в `frontend/styles.css`

## 11. Геймификация: Достижения и Лиги

### 11.1. Обзор системы

Платформа включает полноценную систему геймификации с достижениями (ачивками) и лигами, которая мотивирует пользователей к обучению и практике. Система автоматически отслеживает прогресс и выдаёт награды при выполнении условий.

**Ключевые компоненты:**
- **Достижения (Achievements)** — награды за конкретные действия и достижения на платформе
- **Лиги (Leagues)** — уровни престижа на основе набранных очков (от Бронзы до Мастера)
- **Очки (Points)** — валюта активности, начисляется за выполнение заданий, прохождение курсов и активность в Лаборатории
- **Уровень (Level)** — вычисляется как `1 + floor(points / 500)`

### 11.2. Таблицы базы данных

#### `achievement_definitions`
Справочник всех возможных достижений (сидируется при инициализации БД).

- `id` (TEXT, PK): UUID достижения
- `key` (TEXT, UNIQUE, NOT NULL): уникальный ключ для логики (например `edu_first_course`)
- `category` (TEXT, NOT NULL): категория (`learning`, `practice`, `activity`, `prompting`)
- `title` (TEXT, NOT NULL): название с эмодзи
- `description` (TEXT, NOT NULL): описание условий получения
- `icon` (TEXT, NOT NULL): эмодзи-иконка
- `rarity` (TEXT, NOT NULL): редкость (`common`, `rare`, `epic`, `legendary`)
- `points_reward` (INTEGER, DEFAULT 0): сколько очков начислить при получении
- `hidden` (INTEGER, DEFAULT 0): скрытое ли достижение (1 = да)
- `created_at` (TEXT): дата создания

#### `user_achievements`
Записи о полученных пользователями достижениях.

- `id` (TEXT, PK): UUID записи
- `user_id` (TEXT, NOT NULL): ссылка на `users.id`
- `achievement_id` (TEXT, NOT NULL): ссылка на `achievement_definitions.id`
- `unlocked_at` (TEXT): дата получения
- UNIQUE(`user_id`, `achievement_id`): одно достижение можно получить только один раз

### 11.4. Система лиг

Лиги определяются по сумме набранных очков:

| Лига | Мин. очков | Иконка | Цвет |
|------|------------|--------|------|
| 🥉 Бронза | 0 | 🥉 | #b45309 |
| 🥈 Серебро | 500 | 🥈 | #64748b |
| 🥇 Золото | 1500 | 🥇 | #ca8a04 |
| 💎 Платина | 3000 | 💎 | #38bdf8 |
| 👑 Мастер | 6000 | 👑 | #a855f7 |

При переходе в следующую лигу пользователь получает визуальное отображение прогресса до следующей лиги.

### 11.5. Автоматическая выдача достижений

Система автоматически проверяет условия при:
- Выполнении практического задания (`/api/tasks/submit`)
- Анализе промпта в Лаборатории (`/api/prompts/analyze`)
- Прохождении урока курса
- Загрузке страницы профиля (`/api/profile`)
- Запросе прогресса (`/api/profile/progress`)

**Каскадная система:** При получении достижения начисляются очки, что может автоматически открыть следующее достижение (например, `act_1000_points` → `act_top10`). Система делает до 20 проходов проверки за раз.

### 11.9. Интеграция с другими модулями

**При выполнении задания (`taskController.js`):**
```javascript
// После начисления очков и сохранения результата
const achievements = await evaluateForUser(userId);
// Возвращает массив полученных достижений в ответе
```

**При анализе промпта (`promptController.js`):**
```javascript
// После сохранения анализа
const achievements = await evaluateForUser(userId);
// achievements добавляются в ответ
```

**В профиле пользователя (`profileController.js`):**
- Отображение лиги и прогресса до следующей
- Список последних полученных достижений
- Ближайшие цели (достижения с прогрессом 28-99%)

### 11.10. UI компоненты

**Страница `/leaderboard` включает:**
1. **Топ участников** — таблица с местом, именем, лигой, уровнем, очками и лучшими достижениями
2. **Мой прогресс** — текущая лига, прогресс-бар до следующей, ближайшие цели
3. **Редкие достижения** — подборка достижений с низким процентом владения
4. **Каталог достижений** — все достижения, сгруппированные by категории, с прогрессом и статусом

**Индикаторы редкости:**
- common — серый
- rare — синий
- epic — фиолетовый
- legendary — оранжевый/золотой

## 12. Краткая шпаргалка для нейросетевых сервисов

- **Что это:** образовательная платформа по промпт-инжинирингу (Node/Express + SQLite + статический фронт).
- **Запуск:** `cd backend && npm install && npm start`; открыть в браузере `http://localhost:5000`.
- **Сервер (VPS/хостинг):** см. раздел 9 — `.env` (`JWT_SECRET`, `CORS_ORIGIN=https://…`), PM2/systemd, nginx перед Node; выкладка правок с локальной машины — п. **9.8**.
- **БД:** SQLite, путь в `config.DB_PATH`; схема создаётся в `db/initDB.js`.
- **Админ:** создать скриптом `createAdminUser.js`; все админ-действия через `/api/admin/*` с JWT и ролью `admin`.
- **Анализ промпта:** логика в `utils/aiAnalyzer.js`; при наличии `AI_API_URL` и `AI_API_KEY` — внешний POST `{ prompt }`, иначе эвристики.
- **Фронт:** HTML/CSS/JS в `frontend/`; API-вызовы в `frontend/js/api.js`; токен в `localStorage` под ключом `promptlearn_auth`.
- **Дашборд:** современный админ-дашборд с графиками (Chart.js) по адресу `/admin/dashboard`.

Этого достаточно, чтобы понимать структуру, API, БД и конфигурацию при доработке проекта в других средах и нейросетевых сервисах.
